# Phase 1.5 — Exact Public Host Routing

## Status

Completed locally. Live deployment and browser verification were not executed in this phase.

## Problem

Central public context was available, but all requests still used the default site. A future multi-site deployment could accidentally serve the default site's content on an unrecognized domain.

## Implementation

- PublicSiteContext now accepts an optional exact host map.
- Host names are normalized case-insensitively and trailing dots are handled consistently.
- When a host map is configured, an absent or unknown host fails closed.
- Wildcards, malformed host names and duplicate normalized entries are rejected.
- Public home, content and taxonomy actions pass the request host into the resolver.
- The existing single-site behavior remains unchanged while public.hosts is empty.

## Configuration

The current app keeps public.hosts empty for backward compatibility. A multi-site deployment can explicitly map hosts:

    public:
      site_id: 1
      locale: fa
      hosts:
        fa.example.test:
          site_id: 7
          locale: fa
        en.example.test:
          site_id: 8
          locale: en

The actual Pinoox configuration format remains PHP array syntax in app.php; the example above only shows the shape.

## Remaining risk

Host mapping is now explicit but is still configuration-based. A production multi-site feature should add an admin-managed, audited domain registry and proxy-aware trusted host policy before enabling arbitrary tenant domains.
